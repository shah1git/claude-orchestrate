## Общение агента с владельцем

Пиши на простом, точном русском языке. Явно отмечай неопределённость. Называй одно понятие в одном значении одним каноническим термином. Не заменяй термин синонимом ради разнообразия. Не используй сленг и разговорные гибридные глаголы. Сохраняй без изменений имена технологий, команды, пути, идентификаторы, точные сообщения об ошибках и цитаты. Учитывай адресата и не нарушай явно заданный машинный формат результата.

После технической задачи сообщи статус, существенный результат и состояние проверок. Если формат допускает отдельный отчёт, заверши отчёт строкой `От вас действий не требуется.` либо `От вас требуется: <одно конкретное действие>.`

Следуй полным нормам:

- язык и единый словарь: [`./doctrine/engineering/principles.md`](./doctrine/engineering/principles.md) §3.5;
- канонические термины: [`./doctrine/GLOSSARY.md`](./doctrine/GLOSSARY.md);
- итоговый отчёт технической задачи: [`./doctrine/engineering/agent-reliability.md`](./doctrine/engineering/agent-reliability.md) §1.3.

# claude-orchestrate

Репозиторий скиллов оркестрации и полигона сравнения ролей (`benchmark/`).
Входов в оркестрацию три (ADR-0004, ADR-0006, ADR-0011; прежняя транспортная
голова `orca_orchestrate` выведена, см. [ADR-0008](docs/adr/0008-retire-orca-transport.md)):
полный `/orchestrate` — сырые задачи, голое «оркеструй» и любые нерешённые
решения, подготовительная фаза (грилл → спека → тикеты) в его же сессии; тонкий
`/orchestrate-frontier` — только исполнение готового **опубликованного** фронтира
тикетов с доказуемым происхождением; тонкий `/orchestrate-sweep` — только закрытый
run-local Прочёс с полным локальным ledger, заранее решёнными приёмкой и интеграцией
и явным witness владельца, без tracker provenance. Все три головы работают только
через нативный OMP-контур (ADR-0009): тонкий adapter
`.omp/extensions/pocock-control/`, сохраняемый runtime
`skill/orchestrate/tools/omp_runtime.py` и один запечатанный OMP `task` batch на
раздачу. Конкретные модели контуру неизвестны: он оперирует слотами — ролями
OMP `@pocock-*` (пять слотов), а какая модель стоит
за ролью, задаёт основной конфиг OMP (`$(omp config path)/config.yml`); внешний `run_lane` оставлен как история и
публичными головами не вызывается.

## Agent skills

### Issue tracker

Задачи живут в GitHub Issues этого репозитория (`shah1git/claude-orchestrate`),
операции — через `gh` CLI. Нативные зависимости issue и sub-issues на репозитории
включены и проверены, поэтому карты `/wayfinder` и рёбра блокировки тикетов
выражаются машинно, а не текстовой пометкой в теле. См. `docs/agents/issue-tracker.md`.

### Triage labels

Пять канонических triage-ролей, строка метки совпадает с именем роли. Из них в
трекере пока заведена только `wontfix` (дефолтная гитхабовская); остальные четыре
создаются по мере первого применения. См. `docs/agents/triage-labels.md`.

### Domain docs

Single-context: `CONTEXT.md` и `docs/adr/` в корне репозитория. Сигналов монорепо
нет. См. `docs/agents/domain.md`.

## Конфигурация OMP переносится на другие машины один в один

Рабочие машины владельца держат одинаковое поведение OMP. Поэтому **любая**
правка живого конфига OMP (`$(omp config path)/config.yml`) — порядок и
исключения провайдеров поиска, модели ролей `pocock-*`, инварианты `task`,
таймауты — в том же изменении переносится в закреплённый снимок
`scripts/omp-portable-profile.yml` и коммитится. Снимок обновляется **только**
экспортёром, руками его не правят:

```bash
python3 scripts/export-portable-omp-profile.py   # → scripts/omp-portable-profile.yml
```

Экспортёр читает живой конфиг, отбрасывает машинные корни `dev` и
`setupVersion` и пишет файл лишь после проверки
`scripts/validate_portable_omp_profile.py`. На принимающей машине снимок
раскатывается `bootstrap-machine.sh` (он же обновляет чекаут) или
`./install.sh --configure-omp --configure-pocock-roles`.

Незакоммиченная правка живого конфига — это дрейф: бук получит старое поведение
и разойдётся с этой машиной молча. Автоматическая сверка снимка с живым конфигом
обсуждается в issue #21; до неё правило исполняется вручную, в том же коммите.

## Доктрина RikaNV

Для внешнего читателя: каталог `doctrine/` — локальный клон приватного репозитория
`rikanv-doctrine`, в этом (публичном) репозитории отсутствует. Инструкции блока ниже
действуют в окружении владельца, где клон подключён; для знакомства с проектом снаружи
достаточно `README.md` и `docs/adr/`.

В проекте подключена доктрина `rikanv-doctrine` — единый источник инженерной
дисциплины RikaNV, версия **6.0.0**. Клон в `./doctrine/` (в `.gitignore`;
маркер `.doctrine-version` — коммитится).

С 6.0.0 маркер означает **подтверждённую** ревизию, а проверка перед исходной
задачей стала двухфазной: `start` готовит ревизию и предъявляет статус,
`acknowledge` подтверждает её только после чтения изменившихся **hard**-файлов.
Точный протокол статусов живёт в управляемом блоке «Сессия с доктриной RikaNV»
ниже — он единственный источник этой процедуры, не пересказывайте её своими
словами. Прежнее правило «sync только явной командой владельца» отменено
(ADR-0070 пересматривает ADR-0010 и ADR-0021); `scripts/doctrine-sync.sh`
остаётся для ручной синхронизации по требованию владельца.

Этот репозиторий — **код-инструмент**, поэтому ведущий слой доктрины —
**инженерный**, не бренд-голос (публичного бренд-текста здесь нет; слой
`doctrine/voice/` применяется только если такой текст когда-нибудь появится).
Приборов и их параметров здесь тоже нет, поэтому введённое в 5.2.0 разделение
публичного описания модели и технического источника параметров к этому
репозиторию не применяется: назначать технический источник нечему.

Сверяться при любой не-косметической правке кода:

- [`doctrine/engineering/principles.md`](doctrine/engineering/principles.md) —
  архитектурная чистота (hard): архитектура до кода; контракт — обязательство;
  молчаливые отклонения запрещены (§2.2); **ограничение окружения не аргумент
  против корректности — менять окружение, а не огрублять алгоритм (§2.9)**;
  найденный баг закрывается от повтора регресс-стражем (§2.10); отказ от задачи
  лучше плохого решения (§2.8).
- [`doctrine/engineering/code.md`](doctrine/engineering/code.md) — нормы кода:
  модули, ошибки, документирование, тесты.
- [`doctrine/engineering/agent-reliability.md`](doctrine/engineering/agent-reliability.md)
  — доказательность сделанного (проверка не только выполнена, но и предъявлена),
  восстановление после паузы, калибровка уверенности.
- [`doctrine/engineering/agent-docs.md`](doctrine/engineering/agent-docs.md) —
  когда правишь `AGENTS.md`/`SKILL.md`/README/ADR: явность, разрешимые ссылки,
  понятность агенту любого вендора.

Приоритет при конфликте (ONBOARDING §3, правило 3): глобальный `~/.claude/CLAUDE.md`
задаёт нижнюю планку, `engineering/principles.md` её **ужесточает**; на любом
расхождении проектного правила с доктриной побеждает доктрина. Доктрину из этого
репозитория **не правят** — только PR в `rikanv-doctrine`.

## Сессия с доктриной RikaNV

До исходной задачи запусти session-модуль из корня проекта:

```bash
bash ./doctrine/scripts/doctrine-session.sh start doctrine --status-json
```

`doctrine` необязателен. Если он не указан, session-модуль применяет свой
стандартный путь. Не начинай исходную задачу до обработки единственного JSON-
документа `start`.

### Обработка статуса `start`

- `CURRENT` — доктрина уже актуальна. Не читай документы только ради сессии и
  не отправляй сообщение о состоянии доктрины.
- `PREPARED` — прочитай каждый существующий путь из `documents.hard`,
  подготовленный session-модулем. Затем прочитай `CHANGELOG.md`, если хотя бы
  один hard-путь был удалён либо его dependency была смягчена. После чтения
  выполни точную команду:

  ```bash
  bash ./doctrine/scripts/doctrine-session.sh acknowledge <revisions.prepared>
  ```

  Подставь значение `revisions.prepared` из JSON `start` без сокращения или
  замены. Ожидаемый код `acknowledge` — `ACKNOWLEDGED`. Только этот код может
  изменить `.doctrine-version`; `ACKNOWLEDGEMENT_REJECTED` не подтверждает
  ревизию и не разрешает исходную задачу.

  После ответа с точным кодом `ACKNOWLEDGED` отправь ровно одно сообщение:
  `Доктрина обновилась с <versions.acknowledged> до <versions.prepared>. Изменённые обязательные правила перечитаны.`
  В этом сообщении подставь вместо `<versions.acknowledged>` значение
  `revisions.confirmed` из непосредственно предшествующего ответа `start`, а
  вместо `<versions.prepared>` — точное значение `revisions.prepared` из этого
  ответа `start`; сам текст сообщения не изменяй.
- `READING_REQUIRED` — прочитай каждый существующий путь из `documents.hard`,
  указанный session-модулем, и `CHANGELOG.md`, если хотя бы один hard-путь был
  удалён либо его dependency была смягчена. Затем выполни тот же точный
  `acknowledge <revisions.prepared>`. Не начинай исходную задачу, пока код не
  станет `ACKNOWLEDGED`.
- `NETWORK_UNAVAILABLE` — не пытайся обходить ограничение повторными сетевыми
  вызовами. Продолжай только с доступной подтверждённой ревизией и отправь
  ровно одно сообщение: `Сеть недоступна: актуальность доктрины не подтверждена; используется доступная подтверждённая ревизия.`
- `DIRTY_CHECKOUT`, `UNTRUSTED_CHECKOUT` и `SYNC_FAILED` — остановись. Эти
  состояния блокируют исходную задачу до исправления checkout или синхронизации.

Коды `start` исчерпываются значениями `CURRENT`, `PREPARED`,
`READING_REQUIRED`, `NETWORK_UNAVAILABLE`, `DIRTY_CHECKOUT`,
`UNTRUSTED_CHECKOUT` и `SYNC_FAILED`. Коды `acknowledge` исчерпываются
`ACKNOWLEDGED` и `ACKNOWLEDGEMENT_REJECTED`. Не выводи дополнительных сообщений
о сессии: для `CURRENT` требуется молчание, для успешного обновления требуется
одно сообщение, для ограничения сети требуется одно сообщение.
