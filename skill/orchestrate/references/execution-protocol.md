# Единый протокол исполнения Pocock

Этот протокол применяется после допуска Pocock-прогона любой публичной Головой.
Прямой путь `/orchestrate` в него не входит. Перед первой мутацией runtime Голова
обязана прочитать этот файл и следовать только действиям, разрешённым текущей
Карточкой.

## Дисциплина состояния

Используйте зарегистрированные runtime-инструменты `pocock_*` для каждого изменения
состояния Pocock. В новой OMP-сессии сначала вызовите `pocock_status` **без**
`runId`: ядро находит единственный активный долговечный Прогон рабочего каталога, а
адаптер гидратирует его Карточку. Если возвращённая Карточка содержит
`runtimeMismatch`, вызовите `pocock_enter` для текущей полной цели; ядро
транзакционно журналирует и подготавливает замену до завершения несовместимого
Прогона и активации замены. Если активного Прогона нет, используйте семантику
допуска текущей Головы; в остальных случаях продолжайте только от возвращённой
Карточки.

Несовместимость, доказанная самим ядром — диагностика `runtime_changed` либо
`config_changed` или разошедшийся снимок манифестов агентов, — нативную делегацию
не закрывает: `task` и `hub` остаются доступны для обычной, не-Pocock работы.
Такой Прогон помечается замещаемым; его нельзя ни гидратировать, ни продолжить,
ни отменить, поскольку ядро проверяет отпечаток рантайма раньше `revision` и
`stateHash`. Адаптер объявляет замещаемый Прогон на завершении хода, называя его
`runId`, фазу и причину. Увидев такое объявление, не пытайтесь возобновить или
отменить Прогон и не считайте делегацию заблокированной: единственное
восстановление — `pocock_status`, которым ядро доказывает `runtimeMismatch`, и
затем `pocock_enter` для текущей полной цели.

Любой другой провал гидратации — испорченное зеркало, недоступное ядро,
`state_corrupt` — напротив, закрывает `task` и `hub` наглухо: доверять адаптеру в
этом состоянии нельзя. Это не замещаемый Прогон и не путь восстановления Прогона:
не входите заново, а предъявите блокировку владельцу.

Каждый успешный вызов возвращает текущую Карточку только под ключом `card`.
Сохраняйте её `runId`, новейшие `revision` и `stateHash`; передавайте все три без
изменения в следующем мутирующем runtime-запросе. Действие законно только тогда,
когда последняя Карточка разрешает его в `nextActions`. Никогда не угадывайте
переход состояния, не воспроизводите устаревшее свидетельство, не выбирайте маршрут
исполнителя и не вызывайте runtime CLI напрямую.

Ядро допускает ровно один нетерминальный долговечный Прогон на рабочую область между
OMP-сессиями. Его счётчики попыток и наблюдённый расход токенов принадлежат этому
Прогону и сохраняются при гидратации; новая сессия не может их сбросить. Расход —
только наблюдение: потолка нет, и никакая сумма не запрещает раздачу (ADR-0015).
Если runtime-вызов завершился ошибкой, `stateHash` расходится или Карточка содержит
`blockedReason`, прекратите раздачу и предъявите блокировку. Никогда не отменяйте
и не входите заново автоматически после восстанавливаемой ошибки. Явный отказ
владельца от работы — единственный обычный путь отмены. Новый `pocock_enter` может
заменить активный Прогон только тогда, когда само ядро доказало `runtimeMismatch`:
сначала оно журналирует и подготавливает замену, затем завершает несовместимый
Прогон и активирует подготовленную замену. Никогда не выводите это условие из
ошибки адаптера и не повторяйте старт, отклонённый как `active_run_exists`.

Терминальные фазы runtime — только `completed` и `cancelled`; `complete` является
именем перехода, а не фазой.

## Исполнительный цикл

После публикации, а для другой Головы — после её допуска, используйте этот цикл,
когда текущая Карточка разрешает дальнейшую работу. Подготовка опубликованных
`full` и `frontier` передаёт текущий набор Тикетов из семи полей; подготовка `sweep`
не передаёт Тикеты, поскольку ядро само читает запечатанный ledger и выбирает работу.
Если текущая Карточка показывает законную ветвь, не приведённую в этой компактной
схеме, Карточка имеет приоритет: не выводите и не подменяйте переход.

```text
pocock_prepare
→ producer_dispatch_pending: native task placeholder
→ pregate_pending:
  if evidenceRequests exist: browser open the issued target, then submit the
  issued declarative witness; carry only the current challenge-bound host results
  → pocock_pregate
→ repair_pending: pocock_transition(retry) → pocock_prepare
  or
  lens_prepare_pending: pocock_prepare_lenses
  → lens_dispatch_pending: one wave-level fixed two-lens task
    → if one lens alone fails execution or schema validation, retry only that lens
    → adjudication_pending: pocock_adjudicate
      → repair_pending for affected producer attempts: core routes each by its recorded rejection cause (no separate retry)
        → pocock_prepare
      or accepted producer tickets: pocock_accept
→ pocock_transition(continue_wave) only in the form the current card authorizes:
  published tickets carry tracker-observed remaining/ready/blocked sets plus evidence;
  sweep carries no payload because the runtime-owned sealed DAG computes those sets
→ repeat while work remains; already accepted tickets remain accepted; only an explicit
  empty remaining set authorizes pocock_transition(begin_synthesis) → lead synthesis
  → pocock_transition(complete) → completed
```

Для каждой нативной Pocock-раздачи сделайте ровно один синтаксически корректный, но
семантически пустой вызов `task`. Весь его исходный ввод — только приведённая ниже
заглушка; расширение заменяет её запечатанным ядром вводом задания до передачи:

```text
task({
  context: "Pocock sealed dispatch",
  tasks: [{ task: "Pocock sealed dispatch placeholder" }]
})
```

Не помещайте в этот вызов текст Тикета, маршрутизацию, идентичности, схемы вывода или
результаты. Запечатанный профиль OMP сохраняет глобальные
`task.isolation.apply=false` и `task.isolation.merge=patch`; ядро проверяет и
централизованно применяет возвращённый patch. После завершения блокирующей нативной
`task` она однократна: не ожидайте и не оживляйте её через Hub. Продолжайте только
следующей разрешённой Карточкой runtime-командой; повтор создаёт новую запечатанную
попытку.

### Доверенное UI-свидетельство хоста

Для попытки `ui_live` сначала откройте точную выданную `target` во вкладке с
именем выданного `challengeToken`. Затем единственный допустимый `run` этой
вкладки является **декларативным** вызовом witness версии 1:

```text
{
  action: "run",
  name: challengeToken,
  witness: { version: 1, probe: <нормализуемое декларативное DOM- или URL-наблюдение> }
}
```

Не передавайте исполняемый `assert` в browser-код. Адаптер сам выполняет
browser-assert над фактически наблюдённым `probe` и точным выданным
`criterion`; только его успешный host-result может породить доказательство.
Обычный результат `run`, его текст, проза исполнителя, снимок, текст
утверждения и console.assert не являются доказательством — в том числе если
они содержат критерий или выглядят успешными.

Вызов `run` создаёт одноразовую pending-привязку по его `toolCallId`. После
успешного host-result адаптер потребляет её ровно один раз и передаёт
версионированное свидетельство, структурно связанное с точными `runId`,
`attemptId`, `challengeToken`, `criterion`, `probe` и каноническим
`probeHash`. Повторный результат, другой `toolCallId`, иной challenge, попытка,
критерий или probe не могут использовать эту привязку. Runtime принимает лишь
это текущее полное свидетельство после `open`; legacy-записи и любой неполный
либо несовпадающий контракт отклоняются fail-closed. Затем, и только затем,
запросите `pocock_pregate`.

`pocock_pregate` выполняет запечатанные проверки direct-argv и определяет, какие
попытки Производителей переходят в ревью. `pocock_prepare_lenses` создаёт ровно две
волновые Линзы — Review и Critic — над точно тем
подмножеством, которое прошло pre-gate. Волна может сочетать попытки Производителей
`mechanical`, `skilled` и `judgment` на соответствующих Слотах. Конфигурация делает
множества Слотов Производителей и Линз непересекающимися, а Слоты Линз —
попарно разными. Равенство фактических моделей раздачу не отклоняет: ядро сравнивает
непрозрачные строки до раздачи и повторно после settlement и записывает совпадения как
наблюдение, не классифицируя поставщиков или семейства. Каждая Линза возвращает
`{lens, summary, reports:[{attemptId, summary, findings, verdict}]}` с отчётом для
каждой прошедшей попытки Производителя. Review отвечает на две оси — стандарты
репозитория и соответствие Тикету — и возвращает `NO_VERDICT`,
только Critic возвращает `PASS` или `FAIL`. Если одна Линза отдельно не прошла
исполнение или проверку схемы, только она получает новую запечатанную попытку на том
же Слоте.

Только `pocock_adjudicate` рассматривает отчёты: оно сохраняет уже принятые Тикеты
Производителей и принимает следующий лишь при `PASS` Critic и отсутствии выживших
блокирующих находок Review. Маршрутизация повтора принадлежит коду:
отсутствующий диагноз использует `lastFailureKind`; `capability` повышает класс
Тикета от `mechanical` через `skilled` до `judgment`, кроме пишущего Тикета, который
останавливается на `skilled`; исчерпание допустимой глубины блокируется как
`escalation_exhausted`. `availability` сохраняет Слот и оставляет замену модели OMP.
При частичной приёмке ядро направляет каждый отклонённый Тикет непосредственно по
записанной причине отказа, без отдельного перехода `retry`. Лидер не может ослабить
эти условия; допустимость попытки, лимиты повторов, условия гейта и решение принять
работу принадлежат коду.

Синтезируйте только после того, как runtime разрешит `begin_synthesis`, затем
запросите переход `complete` от возвращённой Карточки. Нетерминальный Прогон никогда
не становится `completed` только потому, что закончилась сессия.

Для каждого терминального Прогона представьте итоговый ledger по Тикетам на языке
пользователя. Для каждого Тикета укажите поставленный результат, его итоговое
состояние приёмки и фактическое доказательство приёмки: применимый запечатанный
результат проверки, принятое UI-доказательство там, где оно требуется, и любую
неразрешённую блокировку или ошибку. Этот ledger описывает поставки и приёмку, а не
историю исполнения: не требуйте и не перечисляйте отдельные попытки, роли, агентов,
заявленные или наблюдённые модели, свидетельства fallback, токены, длительности или
запросы. `observedModel` и `modelFallback` остаются операционной телеметрией живой
Карточки и settlement, а не требованием к финальному ответу. Никогда не создавайте
доказательства.
